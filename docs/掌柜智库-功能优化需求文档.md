### REQ-01: item_name 可选项前端交互优化

**优先级:** P0

**背景:**

当前 `item_name_confirm_service.py:142-165` 中 `confirm_options` 方法已实现双阈值分级逻辑:
- `score >= 0.70`: 直接确认，写入 `confirm_item_name_list`
- `0.60 < score < 0.70`: 写入 `option_item_name_list`

但当前实现中，当存在可选项时，`update_status` 方法仅将可选项拼接为文本写入 `state['answer']`（`item_name_confirm_service.py:183-184`），用户无法交互式选择。前端 `chat.html` 也没有对应的可点击组件。

**需求描述:**

1. **后端改造**: `node_item_name_confirm` 节点在识别到可选项（0.6-0.7 分）时，不直接写入 answer 文本，而是将可选项列表以结构化数据返回，新增 state 字段 `item_name_options: list[str]`
2. **查询图状态扩展**: 在 `QueryGraphState` 中新增 `item_name_options: list[str]` 字段
3. **条件边改造**: `main_graph.py:23-27` 的条件边 `node_item_name_confirm_after` 增加分支判断：当 `item_name_options` 非空时，走向 `node_answer_output` 输出可选项提示
4. **前端交互**: `chat.html` 中当后端返回可选项数据时，渲染为可点击的按钮/标签列表，用户点击后携带选中的 `item_name` 重新发起 `/query` 请求走完整检索流程
5. **SSE 事件扩展**: 新增 SSE 事件类型 `item_options`，将可选项列表实时推送给前端

**涉及文件:**
- `app/rag/query/item_name_confirm_service.py` - 改造 `update_status` 方法
- `app/process/query/agent/state.py` - 新增 state 字段
- `app/process/query/agent/main_graph.py` - 条件边逻辑扩展
- `app/process/query/agent/nodes/node_item_name_confirm.py` - 节点输出改造
- `app/resources/html/chat.html` - 前端可点击组件
- `app/shared/utils/sse_utils.py` - 新增事件类型
- `app/api/http/query_server.py` - 接口响应增加 options 字段
- `app/api/schema/query_schema.py` - Schema 扩展

### REQ-02: MinIO 上传网络图片替代 base64

**优先级:** P1

**背景:**

当前导入流程中 `node_md_img` 节点（`enrich_markdown_images.py`）调用视觉模型（Qwen3-VL-Flash）对 Markdown 中的图片进行描述时，将图片转为 base64 格式传入 LLM。对于大图或多图场景，base64 编码会消耗大量 token，增加成本和延迟。

**需求描述:**

1. **图片上传 MinIO**: 在调用视觉模型前，将图片文件上传至 MinIO，获取可访问的网络 URL
2. **URL 方式传入模型**: 将图片 URL（而非 base64）传入视觉模型 API，减少 token 消耗
3. **上传策略**: 对本地文件路径的图片（如 PDF 解析产物），先上传再引用；对已有网络 URL 的图片直接使用
4. **MinIO 配置复用**: 复用现有 `minio_gateway.py` 和 `minio_config.py` 的配置

**涉及文件:**
- `app/rag/import_/enrich_markdown_images.py` - 核心改造
- `app/infra/object_storage/minio_gateway.py` - 新增上传方法
- `app/shared/clients/minio_utils.py` - 上传工具方法
- `app/process/import_/agent/nodes/node_md_img.py` - 节点适配

### REQ-03: 提示词越权安全防护

**优先级:** P1

**背景:**

当前系统中多个 prompt 模板（`app/resources/prompts/`）直接拼接用户输入和检索结果，存在 prompt injection 风险。恶意用户可能通过构造特殊输入，绕过系统指令获取敏感信息或操控模型行为。

**需求描述:**

1. **输入清洗**: 在所有用户输入进入 LLM 之前，进行安全过滤（移除特殊控制字符、注入标记等）
2. **Prompt 隔离**: 将系统指令与用户输入在 prompt 模板中做明确分隔，使用分隔符和角色标记
3. **输出校验**: LLM 返回结果后，检查是否包含系统 prompt 泄露或越权行为的特征
4. **技术方案**: 待确认，可选方案包括:
   - 方案 A: 基于正则规则的轻量过滤
   - 方案 B: 使用 Guardrails / NeMo Guardrails 框架
   - 方案 C: 双 LLM 架构（Guard LLM + 生成 LLM）

**涉及文件:**
- `app/shared/utils/` - 新增安全工具模块
- `app/resources/prompts/*.prompt` - Prompt 模板安全改造
- `app/rag/query/answer_service.py` - 输出校验
- `app/rag/query/item_name_confirm_service.py` - 输入清洗

### REQ-04: 登录页面 + 白名单权限控制

**优先级:** P0

**背景:**

认证服务 `auth_server.py` 已实现用户注册/登录/JWT Token 等基础能力，MongoDB 用户管理（`mongo_user_utils.py`）也已就绪。但当前存在以下不足:
- 无登录前端页面
- 导入服务（port 8000）无鉴权保护，任何人可上传文件
- 无白名单机制，无法精细控制"谁可以导入文件"

**需求描述:**

1. **登录页面**: 新建 `login.html`，包含用户名/密码输入框、登录/注册切换、Token 本地存储
2. **Token 拦截器**: 前端请求导入服务时自动携带 `Authorization: Bearer <token>` 请求头
3. **导入服务鉴权中间件**: 在 `import_server.py` 中添加 FastAPI 依赖注入中间件，校验 JWT Token 有效性
4. **白名单机制**: 在 MongoDB `users` 集合中新增 `role` 字段（`admin` / `user`），或新建 `whitelist` 集合。仅白名单内用户（或 admin 角色）可调用导入接口
5. **权限分级**:
   - 普通用户: 仅可使用查询服务
   - 白名单用户: 可使用查询服务 + 导入服务
   - admin: 全部权限（含用户管理）
6. **前端跳转**: 未登录用户访问查询/导入页面时，自动跳转至登录页

**涉及文件:**
- `app/resources/html/login.html` - 新建登录页面
- `app/resources/html/chat.html` - 鉴权适配
- `app/resources/html/import.html` - 鉴权适配
- `app/api/http/import_server.py` - 鉴权中间件
- `app/api/http/query_server.py` - 鉴权中间件（可选）
- `app/shared/clients/mongo_user_utils.py` - 用户角色字段扩展
- `app/shared/utils/auth_utils.py` - 角色校验工具

3. **接口扩展**: `GET /status/{task_id}` 响应新增 `progress: float` 字段（0-100）
4. **前端进度条**: `import.html` 中将轮询获取的 `progress` 值实时映射到进度条宽度，替代固定值

**涉及文件:**

### REQ-06: 文档更新哈希校验

**优先级:** P1

**背景:**

当前导入服务接收文件后直接进入全流程处理，未校验文件内容是否已导入过。重复导入相同文件会导致 Milvus 中存在重复向量数据，浪费存储并影响检索质量。

**需求描述:**

1. **文件哈希计算**: 文件上传后，计算 SHA-256 哈希值
2. **哈希记录表**: 在 MongoDB 中新建 `file_hashes` 集合，记录 `{hash, file_name, import_time, task_id, item_name}`
3. **重复校验**: 导入前查询哈希是否已存在:
   - 若存在且内容未变: 跳过导入，返回提示"文件已存在"
   - 若存在但内容变化（同文件名不同哈希）: 执行更新流程，先删除旧向量再导入新数据
4. **哈希更新**: 导入完成后写入/更新哈希记录

**涉及文件:**
- `app/api/http/import_server.py` - 哈希校验逻辑
- `app/shared/clients/` - 新增 `mongo_file_hash_utils.py`
- `app/infra/vectorstore/milvus_gateway.py` - 按 item_name 删除旧向量方法
- `app/process/import_/agent/nodes/node_entry.py` - 入口节点增加校验

### REQ-08: 历史语义相似度匹配

**优先级:** P2

**背景:**

用户可能反复询问语义相同但措辞不同的问题。当前系统每次都走完整检索流程，未利用历史问答记录。

4. **缓存标识**: 复用历史回答时，在前端展示"来自历史缓存"标识

**涉及文件:**
- `app/rag/query/item_name_confirm_service.py` - 相似度匹配逻辑

### REQ-09: 历史记录滞后校验

**优先级:** P1

**背景:**

当知识库文档更新后，之前基于旧文档生成的历史回答可能已过时。需要一种机制判断历史回答的有效性。

**需求描述:**

1. **文档更新时间戳**: 在 MongoDB 中维护 `document_versions` 集合:
   ```json
   {
     "file_name": "xxx.pdf",
     "item_name": "华为P60",
     "last_import_time": "2026-06-12T10:00:00",
     "file_hash": "abc123..."
   }
   ```
2. **历史记录时间戳**: 每条历史记录已包含 `ts` 字段（MongoDB `mongo_history_utils.py` 中的 `datetime` 类型）
3. **滞后判断逻辑**:
   - 用户提问 → 识别 item_name → 查询 `document_versions` 获取该 item_name 的最新导入时间
   - 查询历史记录时，对比历史回答时间与文档更新时间
   - 若 `历史回答时间 < 文档更新时间`: 该历史答案已滞后，跳过历史匹配，直接走向量检索
   - 若 `历史回答时间 >= 文档更新时间`: 历史答案有效，可复用（结合 REQ-08）
4. **实施时机**: 在 `confirm_item_name` 流程中，`load_history` 之后增加滞后过滤

**涉及文件:**
- `app/shared/clients/` - 新增 `mongo_document_version_utils.py`
- `app/rag/query/item_name_confirm_service.py` - 滞后校验逻辑
- `app/process/import_/agent/nodes/node_import_milvus.py` - 入库时记录版本

### REQ-12: 无主体时网络检索 + 前端提示

**优先级:** P0

**背景:**

当前 `item_name_confirm_service.py:168-188` 的 `update_status` 方法中:
- 当 `confirm_item_name_list` 有值时: 正常检索
- 当 `option_item_name_list` 有值时: 返回提示让用户选择
- 当两者都为空时: 返回"您描述的主体不够明确,请重新输出"

第三种情况体验差，用户提问被直接拒绝。理想行为应是：主体识别不到时，自动降级为网络检索。

**需求描述:**

1. **后端逻辑改造**: 修改 `update_status` 方法，当 `confirm_item_name_list` 和 `option_item_name_list` 均为空时:
   - 不写入拒绝文本到 `state['answer']`

   - 设置标记 `state['is_web_only'] = True`
2. **查询图条件边**: `main_graph.py` 的条件边判断增加 `is_web_only` 分支，当为 True 时仅走 `node_web_search_mcp` 路径（跳过向量检索和 HyDE）
3. **前端提示**: 最终回答前增加前缀提示，如: "该问题不在知识库中，以下是网络搜索结果："
4. **SSE 事件**: 新增 `search_mode` 事件，通知前端当前为"纯网络检索"模式

**涉及文件:**
- `app/rag/query/item_name_confirm_service.py` - 核心逻辑改造
- `app/process/query/agent/state.py` - 新增 `is_web_only` 字段

### REQ-13: 公式/特殊内容切片策略

**优先级:** P2

**背景:**

当前 `split_service.py` 的切片策略基于标题层级 + 递归文本分割器（`RecursiveCharacterTextSplitter`），分隔符为 `["\n\n", "\n", "。", "！", "？"]`。对于包含数学公式（LaTeX）、代码块、表格等特殊内容的文档，当前策略可能将公式或代码从上下文中割裂。

**需求描述:**

1. **公式识别**: 在切片前识别 LaTeX 公式（`$...$`、`$$...$$`、`\begin{equation}...`），将公式整体视为一个不可分割的语义单元
2. **代码块保护**: 已有代码块识别逻辑（`split_service.py:67-69`），需确保切片时不拆分代码块内部
3. **表格保护**: 识别 Markdown 表格（`|` 开头的连续行），表格整体保留在同一个 chunk 中
4. **特殊分隔符**: 增加分隔符列表，如 `。` 后优先按 `\n\n` 切分，公式前后作为切分边界

**涉及文件:**
- `app/rag/import_/split_service.py` - 切片策略增强
- `app/process/import_/agent/nodes/node_document_split.py` - 节点适配

### REQ-14: MD 文件提取图片

**优先级:** P2

**背景:**

当导入的源文件为 Markdown 格式时，MD 中可能包含本地图片引用（`![](./images/xxx.png)`）。当前流程中 `node_md_img` 节点会调用视觉模型对图片生成文字描述，但未将图片本身提取并存储到 MinIO 中供前端展示。

**需求描述:**

1. **图片提取**: 解析 Markdown 中的图片引用，提取本地图片文件
2. **上传 MinIO**: 将提取的图片上传至 MinIO，获取永久访问 URL
3. **URL 替换**: 将 Markdown 中的本地图片路径替换为 MinIO URL
4. **关联存储**: 将图片 URL 列表与对应的 chunk 关联存储到 Milvus 的 metadata 中

**涉及文件:**
- `app/rag/import_/enrich_markdown_images.py` - 图片提取与上传
- `app/infra/object_storage/minio_gateway.py` - 上传方法
- `app/process/import_/agent/nodes/node_md_img.py` - 节点改造

### REQ-15: 多格式分流处理节点

**优先级:** P2

**背景:**

当前导入图的路由逻辑（`main_graph.py:25-34`）仅区分 PDF 和 MD 两种格式。随着 REQ-10 引入更多文件格式，需要一种可扩展的分流架构。

**需求描述:**

1. **统一入口路由**: `node_entry` 根据文件扩展名判断类型，设置对应的状态标记（`file_type: str`）
2. **格式处理器注册表**: 使用字典映射 `file_type -> handler_node_name`，实现可插拔的格式处理
3. **条件边扩展**: `node_entry_after_route` 改为基于 `file_type` 的动态路由
4. **共享后处理**: 所有格式处理器输出统一的 `md_content` 和 `md_path`，后续节点（切片→识别→向量化→入库）无需感知原始格式

**涉及文件:**
- `app/process/import_/agent/main_graph.py` - 路由架构改造
- `app/process/import_/agent/state.py` - 新增 `file_type` 字段
- `app/process/import_/agent/nodes/node_entry.py` - 入口路由改造
